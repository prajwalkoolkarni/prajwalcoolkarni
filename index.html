How it works

The council pattern

Every question goes to four specialist models running in parallel — each with a distinct reasoning persona. A fifth synthesizer reads all four responses and distills a single structured answer. The result is closer to how senior engineers actually think: from multiple angles, simultaneously.

The compounding problem

History grows every turn

In a multi-turn conversation, each council call carries the full message history as context. Turn 5 doesn't cost 5× turn 1 — it costs 6×. A 10-question learning session can exhaust most of a day's token budget.

The playbook

Three moves that cut waste

Multi-model reasoning is genuinely more expensive — but the cost is manageable once you understand where it goes. These three strategies matter most.

1
Compress your system prompts

Every token in a system prompt is paid for four times — once per council member. A bloated 200-word persona description costs 1,067 tokens before a single word of the question. Tighten each prompt to its minimum useful length.

A useful heuristic: cut every sentence that doesn't change model behavior. Test the short version — you'll often find the outputs are indistinguishable.

Before: 200-token system prompt × 4 members = 800 tokens After: 50-token system prompt × 4 members = 200 tokens Saving: 600 tokens per question
2
Use a rolling history window

The naïve implementation sends the complete conversation history to every council member on every turn. At turn 10, each of the four models reads 9 previous exchanges before it even sees the new question.

A 2-turn rolling window caps per-turn cost around ~5,000 tokens regardless of session length. You lose some long-range context — worth it for conversations that go deep.

# instead of: messages = system + full_history + question # send: messages = system + last_2_turns + question history_window = conversation_history[-4:] # 2 turns = 4 messages
3
Tier your models by question complexity

Not every question deserves four frontier models. A quick factual lookup doesn't need the same firepower as analyzing a system architecture. You can classify questions before routing: simple → one small model at 10× lower cost, complex → full council.

The fallback chain pattern also helps: primary model first, cheaper backup if it fails. You pay frontier prices only when needed.

models = [ "gemini-2.5-pro", # try first (expensive, capable) "gemini-2.5-flash", # fallback (cheaper, fast) "gpt-4o-mini", # last resort (minimal cost) ]

Takeaway

Powerful doesn't have to mean wasteful.

The ensemble pattern — multiple models, one synthesized answer — is genuinely useful for learning and reasoning. The token cost is real but predictable. Once you understand the compounding effect of history and the multiplier of system prompts, you can build multi-model workflows that scale within a budget.
